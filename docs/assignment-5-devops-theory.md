# The Role of DevOps and CI/CD in Automating Research Projects: the CATS Tangle Simulator

**Assignment 5, Part 1** · Diyas Nurullayev · Group CSE-2507M · Applied Software Development Project · October 2026\
**Project repository:** <https://github.com/PrimeraAizen/cats_sim>

The CATS Tangle Simulator is a Python program that evaluates CATS, a context-aware tip
selection algorithm for DAG-based distributed ledgers, against four published
algorithms. Every number in the CATS paper comes from it. A silent regression, an
upgraded library or a result that nobody can re-run would therefore undermine the
research itself. This report explains how DevOps and CI/CD address that risk, and how
the project applies Docker, Jenkins and Kubernetes.

## 1. What DevOps is: goals, principles and benefits

**DevOps** is a culture and a set of practices that join software development and IT
operations into one shared, largely automated process. The name comes from the first
DevOpsDays conference (2009). DevOps responded to a familiar split: developers wanted
change, operators wanted stability, so releases were rare, large and risky. Its
**goal** is to deliver changes quickly, in small batches, with high reliability and
fast recovery. Its principles are usually summarised as **CALMS**:

| Principle | Meaning for a research project |
| --- | --- |
| Culture | shared ownership: whoever changes the code also keeps the experiments running |
| Automation | build, tests, packaging and deployment run without manual steps |
| Lean | small, frequent changes instead of one large "new version" |
| Measurement | decisions based on data: test coverage, build time, failure rate |
| Sharing | pipelines and server configuration are versioned and visible to everyone |

*The DevOps Handbook* [1] describes the same ideas as three "ways": fast **flow** from
commit to production, fast **feedback** from every stage, and **continual learning**.
The benefits are measurable. Research summarised in *Accelerate* [2] tracks four DORA
metrics: deployment frequency, lead time for changes, change failure rate and time to
restore service. It shows that strong teams are faster *and* more stable, so speed and
reliability are not a trade-off.

## 2. Overview of CI/CD

**Continuous integration (CI)** means merging small changes into a shared mainline at
least daily. Every merge is checked by an automated build and test run, so
integration errors show up within minutes [3]. **Continuous delivery (CD)** keeps
every change that passes the pipeline packaged and ready to release; releasing is a
one-click decision [4]. **Continuous deployment** removes that decision, so every
green change reaches the target environment automatically.

A typical pipeline runs *commit → build → static checks → tests → package → deploy to
a test environment → verify*, and it stops at the first failure. In a good pipeline,
the pipeline itself is code (a `Jenkinsfile` or a workflow YAML) versioned with the
project, fast checks run first, one artifact is built once and promoted unchanged, and
secrets are injected by the CI server instead of being committed.

Common tools include GitHub Actions, GitLab CI/CD and Jenkins, the long-standing
self-hosted, plugin-based automation server [10].

## 3. The role of DevOps tools in research environments

Research software differs from commercial software. Its product is a published
result, its developers are usually scientists without operations staff, and its users
include reviewers who want to reproduce the work years later. Reproducibility is a
real problem: in a *Nature* survey of 1,576 researchers, more than 70% had failed to
reproduce another scientist's experiment [5]. Computational work fails through
dependency drift, "works on my machine" setups, platform-dependent numerics and run
procedures that only one person knows. DevOps tools turn each of these into an
automated, checked step:

| Problem in research | DevOps practice | How CATS applies it |
| --- | --- | --- |
| Environment drift | locked dependencies, container images | `uv.lock` pins every package; the `Dockerfile` also fixes Python 3.14 and Debian |
| Silent regressions in results | tests on every commit | 193 tests, incl. exact equivalence with the original research script; 85% coverage gate |
| Untraceable results | provenance, immutable artifacts | `results.json` stores config, seed and versions; image tag = git commit |
| Manual, undocumented runs | pipelines as code | `Jenkinsfile`; GitHub Actions workflows |
| Setup known to one person | infrastructure as code | Jenkins defined in `jenkins/casc.yaml`; cluster objects in `k8s/` |

The deeper benefit is **trust**. When every figure can be regenerated by one command
from a tagged commit in a fixed environment, reviewers can verify claims instead of
believing them.

## 4. Docker, Jenkins and Kubernetes in scientific and engineering projects

**Docker** packages a program with its interpreter, libraries and operating system
files into an image that runs identically anywhere:

- Boettiger [6] showed how Docker makes R-based analyses portable, and called it
  DevOps practice applied to reproducible research.
- BioContainers distributes bioinformatics tools as containers, so labs can run
  several tool versions on desktops, clouds or HPC [7].
- Di Tommaso et al. [8] showed that genomic pipelines gave *different* results on
  different platforms until containers and the Nextflow workflow manager fixed the
  environment.
- On HPC clusters, where Docker's root daemon is not allowed, Singularity/Apptainer
  runs the same images without root privileges [9].

*In CATS*, a multi-stage `Dockerfile` installs the locked environment with uv and
copies only the virtual environment into a slim, non-root runtime image tagged with
the git commit. `docker run <user>/cats-sim run configs/paper.toml` reproduces the
paper's experiments without installing Python.

**Jenkins** runs pipelines written as code in a `Jenkinsfile`, and its plugins
integrate Git, Docker, Kubernetes and test reports. Being self-hosted, it can run next
to large datasets and inside a laboratory network. The Vera C. Rubin Observatory's
LSST Science Pipelines use Jenkins for continuous integration across their packages
[11]. Their CI includes tests of up to a few hours that run complete pipelines on
small datasets, and "merges are gated on Jenkins builds being successful".

*In CATS*, the Jenkins server is itself code: an image with pinned Jenkins, plugins and
tools, plus Configuration as Code for users, credentials and the job. On every branch
the `Jenkinsfile` runs lint, type checks and Dockerfile lint in parallel, then unit
tests with JUnit and coverage reports, then the image build and a smoke run of the
image. On `main` it also pushes the image to Docker Hub and deploys it.

**Kubernetes** orchestrates containers across a cluster: it schedules them on free
CPUs or GPUs, restarts failed work, and keeps the desired state described in YAML.
Its main scientific value is elastic batch computing. At KubeCon Europe 2019, CERN
engineers re-performed part of the Higgs boson analysis on CMS Open Data. They ran
about 25,000 containerised jobs over roughly 70 TB of data in a public cloud, and the
Higgs mass peak appeared within minutes [12]. The US National Research Platform
offers researchers *Nautilus*, a Kubernetes cluster of about 300 nodes with GPUs, at
no cost [13].

*In CATS*, every green `main` build creates a Kubernetes **Job** on Minikube that runs
the image just pushed to Docker Hub, and the pipeline fails unless the Job completes.
A Job fits a batch simulator better than a long-running Deployment. The namespace
enforces the *restricted* Pod Security Standard, and Jenkins may only manage Jobs in
it. The same manifest could split the hours-long paper experiments across a real
cluster.

## 5. Conclusion: what problems DevOps solves in scientific teams

DevOps does not make research correct, but it removes whole classes of avoidable
failure:

- **reproducibility:** locked dependencies and images fix the environment, so results
  can be regenerated from a tag years later;
- **reliability:** tests on every commit catch regressions before they reach a figure;
- **traceability:** commit → build → image tag → cluster Job → result file links each
  number to the code that produced it;
- **speed:** changes are verified in minutes rather than by hand before a deadline;
- **shared knowledge:** pipelines and servers are code that survives a student's
  graduation;
- **scale:** the same container moves from a laptop to a cluster unchanged.

The costs are real. There is a learning curve, and a self-hosted Jenkins needs updates
and security care. Containers do not make randomised code deterministic: that is the
code's job, and CATS gives every run its own explicitly seeded random stream. Even so,
for a small research team the balance is clearly positive. A few hundred lines of
configuration turned the simulator from "a script that worked once" into a tool that
anyone can test, run and deploy with one command, which is what scientific claims
require.
